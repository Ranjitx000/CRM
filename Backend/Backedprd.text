Backend PRD — Mini ERP + CRM Operations Portal

Stack: Node.js + Express.js + JavaScript + MongoDB (Mongoose)

1. Purpose

Build the REST API and data layer that powers the ERP/CRM portal: authentication, customer records, product/inventory tracking, and the sales challan lifecycle — with correct role-based access and safe concurrent stock handling. The frontend depends entirely on this being correct and stable, so backend ships first.

Stack note: MongoDB is document-based, not relational — transactions and atomicity here rely on Mongoose sessions (multi-document ACID transactions), which require MongoDB to run as a replica set. MongoDB Atlas's free tier is a replica set by default, so this works out of the box; a local single-node mongod does not support transactions unless started as a single-node replica set (rs.initiate()). This is called out explicitly because it's the most common setup mistake with this stack.

5. Core Business Logic Requirements

BL1 — Stock is never edited directly. Product.currentStock changes only as a side effect of inserting a StockMovement document, inside the same session/transaction. No endpoint accepts a raw currentStock update.

BL2 — Challan confirm is atomic and race-safe (Mongoose transaction).

js
// services/challan.service.js
async function confirmChallan(challanId, userId) {
  const session = await mongoose.startSession();
  try {
    let result;
    await session.withTransaction(async () => {
      const challan = await Challan.findById(challanId).session(session);
      if (!challan) throw new AppError(404, 'Challan not found');
      if (challan.status !== 'DRAFT') throw new AppError(409, 'Only draft challans can be confirmed');

      // Atomic per-item stock check + deduct in one conditional update —
      // this is what prevents negative stock under concurrent confirms.
      for (const item of challan.items) {
        const updated = await Product.findOneAndUpdate(
          { _id: item.productId, currentStock: { $gte: item.quantity } },
          { $inc: { currentStock: -item.quantity } },
          { session, new: true }
        );
        if (!updated) {
          throw new AppError(400, `Insufficient stock for SKU ${item.productSkuSnapshot}`);
        }
        await StockMovement.create([{
          productId: item.productId, quantity: item.quantity, type: 'OUT',
          reason: 'Sales Challan', referenceType: 'challan', referenceId: challan._id,
          createdBy: userId,
        }], { session });
      }

      challan.status = 'CONFIRMED';
      challan.confirmedAt = new Date();
      await challan.save({ session });
      result = challan;
    });
    return result;
  } finally {
    session.endSession();
  }
}

The key detail: findOneAndUpdate with currentStock: { $gte: quantity } in the filter makes the check-and-decrement a single atomic operation at the document level — that's what MongoDB uses instead of Postgres's Serializable isolation. Wrapping the whole loop in session.withTransaction ensures that if item 3 of 5 fails, items 1–2's deductions are rolled back too.

BL3 — Challan cancel reverses stock only if it was confirmed. Cancelling a DRAFT challan just marks it CANCELLED (no stock was touched). Cancelling a CONFIRMED challan, inside a transaction, inserts an IN stock movement per item (referenceType: "challan-cancel") and $incs currentStock back up before marking it CANCELLED.

BL4 — Challan items snapshot product data at creation time. productNameSnapshot, productSkuSnapshot, unitPriceSnapshot are copied from the live Product document when the item is added to the draft, and never re-read from Product afterward — even if the product is later edited or repriced.

BL5 — Challan numbering is collision-proof. Use an atomic counter document, not Challan.countDocuments() + 1 (which races under concurrent creates):

js
async function getNextChallanNumber() {
  const year = new Date().getFullYear();
  const counter = await Counter.findByIdAndUpdate(
    `challan-${year}`,
    { $inc: { seq: 1 } },
    { upsert: true, new: true }
  );
  return `CH-${year}-${String(counter.seq).padStart(6, '0')}`;
}

findByIdAndUpdate with $inc is atomic in MongoDB, so this is safe even with two challans being created simultaneously.

6. Validation Rules (Zod, enforced in middleware before controller logic runs)
Reject unknown fields on every body (.strict()).
mobile: required, numeric, length-checked.
email: valid email format when present.
quantity fields: integer, > 0.
unitPrice: positive number.
Enum fields (role, type, status, movementType) validated against the allowed values — invalid values return 400, not a raw Mongoose CastError.
Mongo ObjectId params (:id) validated as a real ObjectId before hitting the DB — invalid format returns 400, not 500.
Pagination page/limit: default page=1, limit=20, limit capped at 100.
7. Error Handling Requirements
Every route wrapped (or uses an asyncHandler wrapper) so thrown/rejected errors reach a single error.middleware.js.
Known errors (AppError with a statusCode) return that code + message.
Mongoose validation errors (ValidationError) mapped to 400 with per-field details.
Mongo duplicate-key errors (E11000, e.g. duplicate SKU/email/challanNumber) mapped to 409 with a clear message, not a raw 500.
Invalid ObjectId (CastError) mapped to 400 ("Invalid id format"), not 500.
Unknown/unexpected errors return 500 with a generic message (never leak stack traces to the client) and are logged server-side.
8. Non-Functional Requirements
Auth security: bcrypt (cost ≥ 10) for passwords; JWT access token ~15 min expiry; refresh token httpOnly + secure cookie, rotated on use.
Rate limiting: /auth/login limited (e.g., 10 attempts / 15 min / IP) via express-rate-limit.
Headers: helmet applied globally.
CORS: restricted to the deployed frontend origin only, not *.
Logging: structured request logging (method, path, status, duration, userId if authenticated); no sensitive fields (passwords, tokens) ever logged.
Indexes: customers.mobile, customers.status, products.sku (unique), stockMovements.productId, challans.status, challans.customerId, challans.challanNumber (unique) — declared in the schemas above.
Transactions: any multi-document write (challan confirm/cancel, stock movement + product stock update) wrapped in a Mongoose session/transaction — requires the MongoDB deployment to be a replica set (true by default on Atlas).
9. Testing Requirements (minimum bar)
Unit: challan confirm logic — sufficient stock (success), insufficient stock (rejected, no partial writes), already-confirmed challan (409).
Integration: concurrency test firing two simultaneous confirms against a product with exactly enough stock for one — exactly one must succeed, the other must fail cleanly, currentStock must never go negative.
RBAC: for each protected route, a test asserting a disallowed role gets 403.
Validation: malformed payloads (missing required field, wrong enum value, negative quantity, invalid ObjectId) return 400 with details.
